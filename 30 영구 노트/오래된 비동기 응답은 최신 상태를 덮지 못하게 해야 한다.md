# 오래된 비동기 응답은 최신 상태를 덮지 못하게 해야 한다

## 주장

같은 화면 상태를 갱신하는 비동기 요청이 겹칠 수 있다면 먼저 시작한 요청이 늦게 끝나더라도 더 최근 의도에서 만들어진 상태를 덮지 못하게 해야 한다. 요청 취소 신호는 불필요한 작업을 줄이고, 별도의 요청 식별자나 cleanup의 ignore 조건은 취소가 늦거나 불가능한 경우에도 결과 적용 순서를 지킨다. React 공식 문서도 Effect의 fetch cleanup에서 요청을 중단하거나 관련 없어진 결과를 무시하라고 설명한다.

## 프로젝트 경험

[[SKN26 Final HumouR AI HR 채용 보조]]의 공유 조회·채팅과 JD 채팅은 새 요청 전에 이전 controller를 중단하고 request id가 현재 값과 일치할 때만 결과를 반영한다. [[HumouR README와 포트폴리오]]에는 요청 취소와 오래된 응답 차단이 개인 경험으로 기록되어 있고, 저장소 구현과 테스트는 그 동작을 보강한다.

## 한계와 반례

취소는 이미 서버에서 수행된 변경을 되돌리지 않으며, 응답을 무시하는 것만으로 중복 결제나 중복 저장 같은 mutation 경쟁을 해결하지 못한다. 이런 부수 효과에는 서버의 멱등 키, 버전 검사나 트랜잭션 경계가 추가로 필요하다. 서로 경쟁하지 않는 단발성 읽기에는 request id가 불필요할 수 있고, TanStack Query 같은 데이터 계층이 신호와 캐시 수명을 관리한다면 컴포넌트마다 같은 제어를 중복 구현하지 않는 편이 낫다.

## 확인한 근거

- 2026-08-11: React 공식 Effect 문서에서 관련 없어진 fetch 결과를 cleanup에서 중단하거나 무시해 늦은 응답이 상태에 영향을 주지 않게 하는 원칙을 확인했다.
- 2026-08-11: MDN에서 `AbortController.abort()`가 완료 전 비동기 작업과 fetch 응답 처리를 중단하는 범위를 확인했다.
- 2026-08-11: TanStack Query 공식 취소 문서에서 query function의 `AbortSignal` 전달과 취소 시 query 상태 복원 동작을 확인했다.
- 프로젝트 코드 확인(개인 해석): `useSharedReportSession.ts`, `JdChatDrawer.tsx`와 관련 테스트에서 controller와 request id를 함께 사용한 결과 적용 경계를 확인했다.
