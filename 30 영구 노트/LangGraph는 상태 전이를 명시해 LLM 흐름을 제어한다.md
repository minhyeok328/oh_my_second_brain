# LangGraph는 상태 전이를 명시해 LLM 흐름을 제어한다

LangGraph를 쓰는 핵심 이유는 LLM 호출을 늘리는 것이 아니라 상태, 노드, 엣지로 다음 실행을 드러내는 데 있다. 공식 Graph API도 상태를 현재 스냅샷, 노드를 계산, 엣지를 다음 노드 결정으로 구분한다. 이 구조를 따르면 분류, 검색, 생성, 재시도 중 어느 단계가 어떤 상태를 읽고 어디로 넘기는지 코드와 로그에서 확인할 수 있다.

[[LangGraph 상태는 노드 사이의 데이터 계약이다]]가 전달할 값을 제한하고, [[조건부 엣지는 상태에 따라 다음 실행 경로를 선택한다]]가 동적 분기를 담당한다. [[RAG의 성능은 검색 단계의 품질에서 시작된다]]처럼 검색과 생성을 분리한 흐름에서는 이 명시적 전이가 실패 위치를 보존한다.

하지만 모든 흐름을 그래프로 만들 필요는 없다. 한 번의 모델 호출과 확정적인 조회로 끝나는 작업은 일반 함수가 더 단순하다. 상태 스키마 없이 노드만 늘리거나 같은 노드에 정적·동적 라우팅을 섞으면 실행 경로가 오히려 불분명해질 수 있으므로, 복잡성이 관찰 가능성과 제어 이득을 넘어서는지 먼저 확인해야 한다.

- 강의 맥락: [[LLM과 RAG 강의]]의 상태 그래프, 도구, 사람 개입, 에이전틱 RAG 실습을 흐름 제어라는 하나의 주장으로 묶었다.
