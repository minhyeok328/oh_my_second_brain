# 질문 인박스

## 답변 상태

아래 항목은 모두 미답변 질문이다. 관찰은 질문이 생긴 맥락이고, 가설은 검증 전 후보일 뿐 영구 지식으로 사용하지 않는다.

## 열린 질문

### 검색 실패와 생성 실패 로그

- 관찰: [[RAG의 성능은 검색 단계의 품질에서 시작된다]]와 [[RAG 평가는 검색과 생성을 분리해서 측정해야 한다]]는 두 단계를 구분한다.
- 가설: 같은 실행 ID에 검색 후보와 생성 출력을 함께 남기면 실패 위치를 나눌 수 있다.
- 질문: 검색 실패와 생성 실패를 어떤 필드로 로그에서 분리할 것인가?
- 답변 상태: 미답변

### 임베딩 모델 변경과 재색인

- 관찰: [[임베딩은 의미 기반 비교를 위한 좌표 표현이다]]와 [[벡터 저장소는 임베딩과 메타데이터를 함께 관리해야 한다]]는 모델과 저장 결과가 연결됨을 보여 준다.
- 가설: 모델 식별자와 인덱스 버전을 같이 기록해야 한다.
- 질문: 임베딩 모델을 바꿀 때 기존 벡터 저장소를 어떤 절차와 완료 기준으로 재색인할 것인가?
- 답변 상태: 미답변

### QuerySet N+1 재현

- 관찰: [[QuerySet은 평가 시점을 늦춰 쿼리 조합을 가능하게 한다]]는 실행 시점과 쿼리 수 확인이 필요하다.
- 가설: 관계 접근 전후의 쿼리 수를 같은 fixture에서 비교할 수 있다.
- 질문: 강의 또는 작은 재현 프로젝트에서 N+1 query를 어떻게 관찰하고 측정할 것인가?
- 답변 상태: 미답변

### React 요청 race condition

- 관찰: [[React API 요청은 로딩 실패 취소 상태를 함께 다뤄야 한다]]는 응답 순서가 화면 상태와 충돌할 수 있음을 다룬다.
- 가설: 지연이 다른 두 요청을 연속 발생시키면 오래된 응답 덮어쓰기를 관찰할 수 있다.
- 질문: race condition을 실제 화면 버그와 테스트로 어떻게 재현할 것인가?
- 답변 상태: 미답변

### Compose 시작 순서와 readiness

- 관찰: [[Docker Compose는 여러 컨테이너의 실행 계약을 한곳에 모은다]]는 서비스 정의와 실제 준비 완료를 구분할 필요가 있다.
- 가설: 포트가 열린 시점과 애플리케이션 healthcheck 성공 시점을 따로 기록할 수 있다.
- 질문: `depends_on`과 readiness 차이를 어떤 최소 실습으로 확인할 것인가?

- 질문: 평가 질문 세트를 프로젝트 DB 변경 주기와 어떻게 동기화할 것인가?
