# 프로젝트 기반 개발자 정체성

## 개인 해석

이 노트는 기존 프로젝트 회고에서 사용자가 남긴 표현을 연결한 개인 서사다. 프로젝트 산출물로 확인되는 사실과 나의 해석을 같은 근거 수준으로 취급하지 않는다.

## 한 줄 요약

프로젝트 경험을 통해 나는 기술 구현만 하는 사람이 아니라, 협업을 위해 문서화와 규칙을 지키려 노력하는 개발자로 정리된다.

## 전환점

가장 큰 전환점은 [[SKN26 2차 신용카드 고객 이탈 분석]]이었다. 2차 프로젝트는 단순히 모델링 기술을 배운 경험을 넘어서, 팀 프로젝트에서는 지켜야 할 규칙과 생각해야 할 비용이 많다는 것을 느끼게 했다.

특히 문서 작업, 커밋 컨벤션, Docker 기반 실행 환경, CLI git, 브랜치 전략을 접하면서 "코드가 돌아가는 것"과 "팀이 함께 유지할 수 있는 것"은 다르다는 감각이 생겼다.

## 계속 지키고 싶은 방식

- 문서화를 가장 먼저 챙긴다. 소통에는 한계가 있으므로 문서는 팀의 공유 기억이 된다.
- dev rules를 미리 정하고 지킨다. 특히 commit, branch, issue, docs는 어떤 프로젝트를 하더라도 포기하지 않을 핵심 규칙이다.
- 도구를 쓰는 이유를 이해하려 한다. Docker, MLflow, GitHub 규칙은 처음에는 어렵지만, 한 번 겪으면 다음 프로젝트의 속도를 올려준다.
- 기능 구현 결과뿐 아니라 팀원이 이어받을 수 있는 형태인지 확인한다.

## 포기 못할 Dev Rules

- [[개인 Dev Rules]]: commit, branch, issue, docs를 중심으로 정리한 개인 협업 운영 원칙
- commit: 변경 이유를 추적할 수 있게 남긴다.
- branch: 작업 흐름을 섞지 않는다.
- issue: 작업의 시작점과 완료 기준을 남긴다.
- docs: 팀의 공유 기억을 최신 상태로 유지한다.

## 포트폴리오에서 보여주고 싶은 모습

기술도 중요하지만, 나는 협업을 위해 정말 많이 노력하는 사람으로 평가받고 싶다. LLM/RAG, 프론트엔드, 데이터 분석 같은 기술 경험은 프로젝트의 표면이고, 그 아래에는 문서화, 규칙 정리, GitHub 운영, QA 리스크 기록처럼 팀 작업을 유지하려는 태도가 있다.

면접이나 포트폴리오에서는 다음 문장으로 설명할 수 있다.

> 저는 기술 구현뿐 아니라 팀이 같은 방향으로 움직이도록 문서와 규칙을 정리하는 데 에너지를 많이 쓰는 개발자입니다.

## 프로젝트 근거

- [[SKN26 1차 차량 운영비 프로젝트]]: 기술 기반이 부족한 상태에서도 API 수집과 기본 구현 흐름을 끝까지 경험했다.
- [[SKN26 2차 신용카드 고객 이탈 분석]]: 문서화, 커밋 컨벤션, Docker, CLI git, 브랜치 전략을 통해 팀 프로젝트의 규칙 비용을 체감했다.
- [[SKN26 3차 PICKLE 맛집 추천 챗봇]]: RAG 평가와 후보 밖 답변 금지를 통해 LLM 시스템은 답변보다 검증 구조가 중요하다는 감각을 얻었다.
- [[SKN26 4차 LG Home AI 가전 상담]]: 프론트엔드, 문서 작업, GitHub 조직 관리를 맡으며 협업 구조를 관리하는 역할을 경험했다.

## 실패 조건

- 문서가 최신 상태가 아니면 오히려 팀의 오해를 늘린다.
- dev rules가 이유 없이 강제되면 협업 장치가 아니라 부담이 된다.
- 규칙을 정했지만 검토하지 않으면 커밋 컨벤션, 브랜치 전략, QA 기준이 금방 흐려진다.
- "협업을 위해 노력했다"는 말이 실제 산출물, 문서, GitHub 운영 기록으로 이어지지 않으면 포트폴리오 설득력이 약해진다.

## 먼저 확인할 질문

- 지금 팀원이 새로 들어와도 이 프로젝트를 실행하고 이해할 수 있는 문서가 있는가?
- 커밋, 브랜치, PR, 이슈, QA 기준이 말로만 정해진 것이 아니라 실제 기록으로 남아 있는가?
- 내가 맡은 역할이 기능 구현뿐 아니라 협업 비용을 줄인 사례로 설명되는가?
