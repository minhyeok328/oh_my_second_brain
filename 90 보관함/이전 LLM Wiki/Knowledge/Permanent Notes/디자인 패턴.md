# 디자인 패턴

태그: #designpattern #oop #llm_wiki

## 한 줄 정의

소프트웨어 설계에서 반복되는 문제에 대한 재사용 가능한 해법과 이름의 모음이다.

## 왜 중요한가

패턴은 코드 암기가 아니라 의사소통 도구다. 생성, 구조, 행위 패턴을 구분하면 객체 협력 방식을 빠르게 파악할 수 있다.

## 핵심 개념

- 생성 패턴은 객체 생성 책임을 다룬다.
- 구조 패턴은 객체 조합과 인터페이스 변환을 다룬다.
- 행위 패턴은 객체 간 책임 분배와 알고리즘 교체를 다룬다.

## 예제

```text
문제 -> 책임 분리 -> 참여 객체 -> 협력 방식 -> 장단점
```

## 실무 활용

Java/Python 실습 예제를 넘어 Django 서비스, React 컴포넌트, 에이전트 도구 구조 설계에 응용한다.

## 내 말로 다시 설명

디자인 패턴은/는 강의에서 나온 개념을 정의, 사용 조건, 주의점, 연결 개념으로 다시 설명하기 위한 LLM wiki 원자 노트다. 단순 암기보다 실제 문제에서 언제 꺼내 쓸지 판단하는 데 초점을 둔다.

## 언제 쓰는가

- 강의 실습 코드에서 같은 개념을 다시 만날 때
- 프로젝트에서 관련 오류나 설계 결정을 설명해야 할 때
- [[Singleton Pattern]], [[Adapter Pattern]], [[Strategy Pattern]]와 함께 문제 원인을 좁힐 때

## 언제 쓰면 안 되는가

- 구체적인 API 버전, 파라미터, 보안 정책이 필요한 경우에는 공식 문서를 먼저 확인한다.
- 예제 하나만 보고 모든 상황에 일반화해야 할 때는 보류한다.
- 이미 더 좁고 구체적인 노트가 있는 경우에는 그 노트로 이동한다.

## 자주 헷갈리는 점

- 이름이 비슷한 인접 개념과 책임 범위가 다를 수 있다.
- 강의 예제의 상황과 실제 프로젝트의 데이터, 환경, 버전 차이를 분리해야 한다.
- "동작한다"와 "운영에서 유지보수 가능하다"는 다른 기준이다.

## 확인 질문

- 디자인 패턴을/를 쓰면 어떤 문제를 더 단순하게 설명할 수 있는가?
- 관련 개념과 구분되는 핵심 기준은 무엇인가?
- 실제 프로젝트에 적용하면 먼저 검증해야 할 실패 조건은 무엇인가?
