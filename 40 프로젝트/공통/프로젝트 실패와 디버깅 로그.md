## 미확인 디버깅 후보 — 1차 차량 TCO

- 상황: 검색 조건 변경과 Streamlit rerun 뒤 선택 상태가 오래 남거나 외부 데이터가 비어 계산이 깨질 가능성을 점검한다.
- 선택 또는 원인: 미확인 원인 후보는 session state 초기화 누락, 문자열 결합 SQL, API key·응답·selector 변경이다.
- 근거: [[SKN26 1차 차량 운영비 프로젝트]], [[Streamlit 세션 상태는 재실행 사이의 값을 보존한다]], [[HTTP 요청은 타임아웃과 실패 처리를 기본값으로 가져야 한다]].
- 결과: 미확인 — 실제 장애 발생 기록이나 재현 결과로 확정하지 않는다.
- 다음에 적용할 원칙: 상태 전이, parameter binding, timeout·status·필수 필드와 fallback을 재현 절차와 함께 확인한다.

### 개인 해석

API 수집을 맡았지만 1차 당시에는 코딩, AI, 에이전트 모두 익숙하지 않아 전반적인 난도가 높았다. 이 경험은 "코드는 직접 많이 작성하고 실험해야 익숙해진다"는 깨달음으로 남았다.

## 미확인 디버깅 후보 — 2차 카드 이탈 예측

- 상황: 전체 정확도와 train 성능이 좋아도 소수 class 또는 test 성능이 약할 가능성을 점검한다.
- 선택 또는 원인: 미확인 원인 후보는 class 불균형, 과적합, feature 누수, Unknown Income의 의미 혼동과 MLflow artifact 식별자 불일치다.
- 근거: [[SKN26 2차 신용카드 고객 이탈 분석]], [[분류 평가는 클래스 불균형에 맞는 지표를 선택해야 한다]], [[학습 데이터와 평가 데이터는 모델 선택 전에 분리해야 한다]], [[MLflow는 실험 조건과 결과를 함께 추적한다]].
- 결과: 미확인 — 원인별 재실험 결과가 이 로그에 기록되지 않았다.
- 다음에 적용할 원칙: accuracy와 소수 class recall·F1을 함께 보고, split·artifact·flavor를 실험 ID와 함께 기록한다.

### 개인 해석

당시에는 이탈자 예측이라는 목적 때문에 정확도를 더 집중적으로 확인하려 했던 것으로 기억한다. 성능이 낮게 나왔을 때 가장 먼저 떠올린 원인은 class 불균형이었다. Unknown은 시각화상 관계에 끼치는 영향이 커서 단순 삭제하기 어렵다고 느꼈다.

## 미확인 디버깅 후보 — 3차 PICKLE RAG 챗봇

- 상황: 질문이 잘못된 route로 가거나 slot·검색 후보·최종 답변 중 한 단계에서 기대 결과를 놓칠 가능성을 점검한다.
- 선택 또는 원인: 미확인 원인 후보는 route 기준, payload schema, DB 검색 경로와 후보 밖 생성이다.
- 근거: [[SKN26 3차 PICKLE 맛집 추천 챗봇]], [[RAG 검색 실패 사례]], [[RAG 평가는 검색과 생성을 분리해서 측정해야 한다]].
- 결과: 미확인 — 개별 질문의 재현 입력과 평가 결과를 추가해야 한다.
- 다음에 적용할 원칙: route, payload, target, retrieval, answer를 같은 실행 ID로 기록하고 후보 밖 답변을 별도 실패로 센다.

### 개인 해석

fixed route는 구현 후에도 굳이 필요했는지 의문이 남았다. 실제로 가장 어렵게 느껴진 축은 answer였고, 후보 밖 답변 금지를 가장 신경 써야 한다고 느꼈다.

## 미확인 디버깅 후보 — 4차 LG Home

- 상황: 후속 질문 state, 상품 DB와 매뉴얼 검색 분기, AJAX·CSRF·세션 만료와 SSR 파일 책임을 점검한다.
- 선택 또는 원인: 미확인 원인 후보는 이전 조건 병합, intent 분기, CSRF·credentials·content type·error payload 처리와 template·static JS 책임 분산이다.
- 근거: [[SKN26 4차 LG Home AI 가전 상담]], [[Django 챗봇은 대화 상태와 요청 경계를 함께 관리해야 한다]], [[CSRF 방어는 브라우저 세션 요청의 출처를 검증한다]], [[Django JSON API는 화면과 서버 책임을 분리한다]].
- 결과: 미확인 — 프로젝트 허브에 남은 QA 범위와 실제 재현 결과를 구분해 추가해야 한다.
- 다음에 적용할 원칙: 입력 state, intent, 검색 대상, HTTP 상태와 사용자에게 보인 오류를 한 요청 단위로 기록한다.

### 개인 해석

4차 챗봇에서는 후속 질문 처리가 가장 어렵게 느껴졌다. SSR 구조에서 특별히 편한 점은 크지 않았고, 관리 파일이 많아진 점이 가장 불편했다. React SPA 전환은 공식 팀 프로젝트가 아니라 프로젝트 종료 후 혼자 해본 재공학 경험이다.
