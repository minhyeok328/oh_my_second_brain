# 프로젝트 실패와 디버깅 로그

태그: #project_context #project #failure #debugging #experience

## 기록 기준

이 문서는 실제 코드 구조와 프로젝트 노트에서 확인되는 실패 조건을 정리한다. 실제로 어떤 장애가 발생했는지, 당시 어떤 감정이나 협업 맥락이 있었는지는 사용자의 추가 회고가 필요하다.

## 1차 차량 TCO

### 상태 관리 실패

- 증상 후보: 검색 후 선택한 차량이 rerun 이후 사라지거나, 검색 조건 변경 뒤 이전 차량 정보로 비용이 계산된다.
- 확인 위치: `main.py`의 `st.session_state["in_oil"]`, `in_price`, `open_result`
- 먼저 볼 것: 검색 조건이 바뀔 때 기존 선택 상태를 초기화하는가?
- 연결 노트: [[Streamlit Session State]]

### DB 검색 안전성

- 증상 후보: 모델명에 따옴표나 wildcard가 들어가면 SQL 오류 또는 부정확한 검색이 발생한다.
- 확인 위치: `DBLoader.py`의 `model_name like '%{user_input}%'`
- 먼저 볼 것: 사용자 입력을 parameter binding으로 처리하는가?
- 연결 노트: [[MySQL Connector Python]], [[SQL SELECT와 WHERE]]

### 외부 데이터 실패

- 증상 후보: API key 누락, 공공 API 응답 구조 변경, HTML selector 변경으로 빈 결과나 파싱 오류가 난다.
- 확인 위치: `CarOil.py`, `CarPrice.py`, `OilPrice.py`
- 먼저 볼 것: status check, timeout, 필수 필드 검증, fallback 메시지가 있는가?
- 연결 노트: [[Requests]], [[동적 웹 스크래핑]]
- 개인 회고: API 수집을 맡았지만 1차 당시에는 코딩, AI, 에이전트 모두 익숙하지 않아 전반적인 난도가 높았다. 이 경험은 "코드는 직접 많이 작성하고 실험해야 익숙해진다"는 깨달음으로 남았다.
- 설명 포인트: 기술적으로 완벽하지 않았더라도 기본을 지키며 끝까지 구현하려 한 프로젝트로 설명할 수 있다.

## 2차 카드 이탈 예측

### Accuracy 착시

- 증상 후보: 전체 정확도는 높아도 이탈 고객이나 소수 class를 놓친다.
- 확인 위치: `model_evaluation.md`의 accuracy, recall, F1, ROC-AUC 비교
- 먼저 볼 것: 문제 목적이 소수 class 탐지인지 전체 평균 성능인지 분리했는가?
- 연결 노트: [[분류 평가 지표]]
- 개인 회고: 당시에는 이탈자 예측이라는 목적 때문에 정확도를 더 집중적으로 확인하려 했던 것으로 기억한다. 다음 검증에서는 정확도와 함께 이탈자 class의 recall, F1을 반드시 같이 봐야 한다.

### Train/Test 성능 차이

- 증상 후보: train 성능은 높지만 test 성능이 낮아 실제 예측력이 약하다.
- 확인 위치: multi-class income train/test 지표 차이
- 먼저 볼 것: feature 누수, class 경계 모호성, 과적합 가능성을 나눠 봤는가?
- 연결 노트: [[Train Test Split]], [[과적합]]
- 개인 회고: 성능이 낮게 나왔을 때 가장 먼저 떠올린 원인은 class 불균형이었다.

### Unknown Income 처리

- 증상 후보: Unknown을 학습 라벨처럼 넣거나 단순 삭제해 데이터 해석이 흔들린다.
- 확인 위치: `model_evaluation.md`의 known/unknown 분리
- 먼저 볼 것: Unknown은 결측인가, 별도 의미가 있는 class인가, 예측 적용 대상인가?
- 연결 노트: [[Feature Engineering]], [[데이터 전처리]]
- 개인 회고: Unknown은 시각화상 관계에 끼치는 영향이 커서 단순 삭제하기 어렵다고 느꼈다. 다시 한다면 군집화, 차원축소, 모델링을 더 다양하게 비교해 결측치 예측 결과를 명확히 마무리하고 싶다.

### MLflow artifact 로드 실패

- 증상 후보: 대시보드에서 최신 모델을 찾지 못하거나 모델 flavor가 달라 로드가 실패한다.
- 확인 위치: `streamlit\common\mlflow\load_latest_model_by_name.py`
- 먼저 볼 것: run name, experiment name, artifact path, flavor fallback이 맞는가?
- 연결 노트: [[MLflow]]
- 개인 회고: MLflow, Docker Compose, CLI git, 브랜치 전략이 모두 처음이라 도구 자체를 이해하는 데도 시간이 들었다. 그래도 한 번 겪은 어려움이 이후 프로젝트에서 협업 환경을 더 편하게 다루는 기반이 되었다.

## 3차 PICKLE RAG 챗봇

### Route 실패

- 증상 후보: 특정 식당/메뉴 질문이 embedding으로 가거나, 분위기 질문이 fixed로 가서 검색이 빗나간다.
- 확인 위치: `src\router.py`, `src\pipeline.py`
- 먼저 볼 것: 질문 유형과 route label이 goldset 기대값과 맞는가?
- 연결 노트: [[조건부 엣지는 상태에 따라 다음 실행 경로를 선택한다]], [[RAG 평가는 검색과 생성을 분리해서 측정해야 한다]]
- 개인 회고: fixed route는 구현 후에도 굳이 필요했는지 의문이 남았다. route를 나누는 기준이 명확하지 않으면 품질 개선보다 복잡도 증가로 이어질 수 있다.

### Payload 추출 실패

- 증상 후보: slot key가 비거나 잘못 채워져 검색 후보가 과도하게 넓거나 좁아진다.
- 확인 위치: slot extraction node, `database\sql\utils.py`
- 먼저 볼 것: route별로 기대하는 payload schema가 다르지 않은가?
- 연결 노트: [[함수 호출은 자연어 요청을 구조화된 도구 입력으로 바꾼다]], [[LangGraph 상태는 노드 사이의 데이터 계약이다]]

### Retrieval/Answer 불일치

- 증상 후보: 검색 후보에는 정답이 있는데 답변이 다른 식당을 말하거나 후보 밖 내용을 만든다.
- 확인 위치: `evaluate_llm.py`의 target, answer, retrieval check
- 먼저 볼 것: 답변 생성 프롬프트가 후보 dict 밖 지식을 금지하는가?
- 연결 노트: [[RAG의 성능은 검색 단계의 품질에서 시작된다]], [[검색기는 질문과 관련된 근거 후보를 좁힌다]], [[RAG 검색 실패 사례]]
- 개인 회고: 실제로 가장 어렵게 느껴진 축은 answer였다. RAG의 핵심은 hallucination 방지이므로, 후보 밖 답변 금지를 가장 신경 써야 한다.

## 4차 LG Home

### 후속 질문 state 실패

- 증상 후보: 사용자의 다음 질문이 이전 조건을 잘못 이어받거나 새 질문을 후속 질문으로 착각한다.
- 확인 위치: `common\llm.py`, `common\llm_agent.py`
- 먼저 볼 것: 이전 state와 현재 질문의 제품군, intent, slot 병합 규칙이 명확한가?
- 연결 노트: [[LangGraph 상태는 노드 사이의 데이터 계약이다]], [[Django Chatbot]]
- 개인 회고: 4차 챗봇에서는 후속 질문 처리가 가장 어렵게 느껴졌다.

### 상품 DB 검색과 매뉴얼 RAG 혼동

- 증상 후보: 상품 추천 질문에 매뉴얼 chunk를 답하거나, 사용설명서 질문에 상품 DB 조건만 적용한다.
- 확인 위치: `common\llm.py`, `common\vector_search.py`
- 먼저 볼 것: 질문 intent가 DB 검색인지 manual RAG인지 분기되는가?
- 연결 노트: [[RAG의 성능은 검색 단계의 품질에서 시작된다]], [[벡터 저장소는 임베딩과 메타데이터를 함께 관리해야 한다]], [[Django QuerySet]]

### AJAX/CSRF 실패

- 증상 후보: JSON API 호출이 403, redirect HTML, JSON parse 오류, 네트워크 실패로 깨진다.
- 확인 위치: `api\views.py`, `static\js\api-response.js`
- 먼저 볼 것: CSRF token, credentials, 로그인 상태, content-type, error payload를 공통 처리하는가?
- 연결 노트: [[Django CSRF]], [[Django JSON API]], [[React API Fetch]]
- QA 근거: `docs\03-frontend\frontend-final-report.md`는 챗봇 세션 만료 401 시 로그인 유도 부재를 최우선 잔여 개선점으로 둔다. `fetchJson` 공통화, 필터 에러 배너, 찜 in-flight는 개선됐지만 401/세션 만료, 모바일 실기기, 회원가입·비밀번호 찾기 검증은 추가 확인이 필요하다.

### 공식 프로젝트와 개인 확장 근거 혼동

- 증상 후보: Django SSR 공식 프로젝트 경험과 React SPA 개인 확장 경험이 한 문장 안에서 섞인다.
- 확인 위치: [[SKN26 4차 LG Home AI 가전 상담]]의 `source`, `related_source`
- 먼저 볼 것: 공식 산출물 기준인지, 프로젝트 종료 후 개인 실험 기준인지 분리했는가?
- 연결 노트: [[React SPA]], [[Django JSON API]]
- 개인 회고: React SPA 전환은 공식 팀 프로젝트가 아니라, 공식 프로젝트 종료 후 혼자 해본 재공학 경험이다.

### SSR 파일 관리 복잡도

- 증상 후보: 화면을 React 없이 Django template, partial, static JS로 나누면서 기능 하나를 고치기 위해 확인해야 할 파일이 많아진다.
- 확인 위치: `templates\`, `templates\components\`, `static\js\`, `docs\03-frontend`
- 먼저 볼 것: 공통 컴포넌트, 페이지별 JS, 인라인 스크립트의 책임이 분리되어 있는가?
- 연결 노트: [[Django Template]], [[React SPA]]
- 개인 회고: SSR 구조에서 특별히 편한 점은 크지 않았고, 관리 파일이 많아진 점이 가장 불편했다.
