## 프로젝트 경험 — 1차 차량 TCO의 상태와 데이터 경계

- 상황: 검색, 차량 선택, 가격과 주행 패턴 선택, 비용 계산이 Streamlit rerun을 넘어 이어져야 했다.
- 선택 또는 원인: `st.session_state`로 화면 상태를 유지하고, DB 접근을 `DBLoader.py`로 분리했으며 차량 모델은 부분 검색으로 찾았다.
- 근거: [[SKN26 1차 차량 운영비 프로젝트]], [[Streamlit 세션 상태는 재실행 사이의 값을 보존한다]], [[MySQL Connector는 SQL 실행과 트랜잭션 경계를 명시해야 한다]].
- 결과: 외부 차량·가격·유가 데이터를 DB 조회와 월간 TCO 계산 흐름에 연결했다.
- 다음에 적용할 원칙: 검색 조건 변경 시 초기화할 상태, parameter binding, 외부 데이터 실패 시 중단·경고 기준을 먼저 정한다.

### 개인 해석

1차 프로젝트에서 직접 맡은 부분은 API 수집이었다. 첫 프로젝트라 기술 기반이 충분하지 않았지만, 외부 데이터를 가져와 계산 흐름에 붙이는 역할을 맡으며 기본 구현 흐름을 익혔다.

## 프로젝트 경험 — 2차 카드 이탈의 문제 재구성

- 상황: Unknown Income과 여러 income class를 어떻게 다룰지, 모델과 실행 환경을 어떻게 비교·재현할지 결정해야 했다.
- 선택 또는 원인: Unknown을 바로 삭제하지 않고 known·unknown을 나누어 보며, multi-class와 Low·High binary 구성을 비교하고 Streamlit·MLflow·pipeline API·DB를 Compose 서비스로 분리했다.
- 근거: [[SKN26 2차 신용카드 고객 이탈 분석]], [[특성 공학은 모델보다 먼저 데이터 표현을 개선한다]], [[학습 데이터와 평가 데이터는 모델 선택 전에 분리해야 한다]], [[MLflow는 실험 조건과 결과를 함께 추적한다]].
- 결과: 고객 행동 지표 중심의 분석, 모델 비교와 분리된 실행 구성이 기존 프로젝트 기록에 남았다.
- 다음에 적용할 원칙: class 재구성의 비즈니스 의미, 소수 class 지표와 데이터 손실을 성능 수치와 함께 기록한다.

### 개인 해석

관계를 시각화했을 때 Unknown이 변수 해석에 끼치는 영향이 커서 없애기에는 부담이 컸다. 성능이 낮을 때 가장 먼저 의심한 것은 class 불균형이었다. MLflow, Docker Compose, CLI git과 브랜치 전략은 처음이라 어려웠지만 이후 프로젝트에서 협업 도구를 받아들이는 기반이 되었다.

## 프로젝트 경험 — 3차 RAG 경로와 평가 분리

- 상황: 특정 식당·메뉴 질문과 분위기·상황 기반 질문의 검색 방식이 달랐고 실패 위치를 분리할 필요가 있었다.
- 선택 또는 원인: fixed와 embedding route를 나누고 LangGraph로 route, slot, search, generate 노드를 구분했으며 goldset에서 route, payload, target, answer, retrieval을 따로 보았다.
- 근거: [[SKN26 3차 PICKLE 맛집 추천 챗봇]], [[LangGraph는 상태 전이를 명시해 LLM 흐름을 제어한다]], [[RAG 평가는 검색과 생성을 분리해서 측정해야 한다]].
- 결과: 검색 경로와 평가 축을 단계별로 추적하는 기존 구조가 만들어졌다.
- 다음에 적용할 원칙: route 분리가 실제 품질 이득을 만드는 질문 유형을 먼저 정의하고, 후보 밖 답변을 별도 실패로 기록한다.

### 개인 해석

fixed route는 구현 후에도 굳이 필요했는지 의문이 남았다. node를 나누면 route, slot, search, generate를 단계별로 볼 수 있어 관리와 디버깅이 쉬워졌다고 느꼈고, 평가 축 중에서는 answer가 생각보다 어렵게 느껴졌다.

## 프로젝트 경험 — 4차 SSR과 검색 책임 분리

- 상황: 공식 팀 산출물의 Django 화면, 상품 DB 검색과 매뉴얼 검색의 책임을 구분해야 했다.
- 선택 또는 원인: 공식 프로젝트는 Django template·view·static JS를 사용한 SSR로 유지하고, 상품 추천의 DB 검색과 사용설명서의 매뉴얼 검색을 다른 경로로 두었다.
- 근거: [[SKN26 4차 LG Home AI 가전 상담]], [[QuerySet은 평가 시점을 늦춰 쿼리 조합을 가능하게 한다]], [[벡터 저장소는 임베딩과 메타데이터를 함께 관리해야 한다]].
- 결과: 공식 프로젝트의 SSR 구조와 프로젝트 종료 후 React 확장 경험이 구분되어 기록됐다.
- 다음에 적용할 원칙: 공식 산출물과 개인 확장의 출처, DB 검색과 RAG 검색의 입력·출력 계약을 명시한다.

### 개인 해석

공식 프로젝트에서 맡은 범위는 프론트엔드 파트, 문서 작업, GitHub 조직 관리였다. SSR 구조에서 특별히 편하다고 느낀 점은 크지 않았고, React 없이 구조를 맞추며 관리해야 할 template와 static JS 파일이 많아진 점이 불편했다. 모델링 쪽은 직접 맡지 않아 잘 모른다는 경계도 유지한다.

## 개인 해석 — 4차 이후 React 확장

- 상황: 공식 프로젝트 종료 후 Django template SSR 방식이 아닌 React 분리 구조를 시험하고 싶었다.
- 선택 또는 원인: `4th_project_change_react`에서 프론트 렌더링과 Django JSON API 책임을 분리했다.
- 근거: [[SKN26 4차 LG Home AI 가전 상담]]의 개인 확장 기록, [[React SPA는 화면 상태와 서버 상태의 경계를 분명히 해야 한다]], [[Django JSON API는 화면과 서버 책임을 분리한다]].
- 결과: React SPA로 분리해 보니 Django는 화면 조립보다 DB, 인증, LLM 호출 결과를 JSON API로 제공하는 쪽이 더 명확해 보였다는 기존 회고가 남았다.
- 다음에 적용할 원칙: 개인 확장을 공식 팀 프로젝트의 역할이나 결과로 합치지 않는다.
