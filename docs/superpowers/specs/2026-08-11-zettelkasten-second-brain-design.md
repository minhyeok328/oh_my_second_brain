# Zettelkasten Second Brain 전환 설계

## 1. 배경

현재 Obsidian 볼트는 `Knowledge` 아래 312개의 Markdown 노트를 중심으로 구성된 LLM Wiki다. 이 중 233개가 Permanent Note이며, 199개는 `wiki-standardized` 상태의 자동 표준화 노트다. 활성 구조에는 LLM 검색 정책, 검색 스코프, 품질 게이트, 보강 백로그와 생성 보고서가 포함되어 있다.

전환에 사용할 원본 자료는 다음 두 위치다.

- 강의 자료: `C:\MinHyeok\lecture` — 12개 강의 영역, 891개 파일
- 프로젝트 자료: `C:\MinHyeok\skn26_projects` — 1차부터 Final까지 5개 프로젝트, 996개 파일

프로젝트의 개인 기여, 기술적 판단과 회고는 프로젝트 루트 README와 공개 포트폴리오 `https://minhyeok328.github.io/`를 함께 사용한다.

## 2. 목표

- LLM Wiki 운영 계층을 제거하고 개인용 Second Brain으로 전환한다.
- Zettelkasten 방식으로 빠른 기록, 소스 노트, 영구 노트와 구조 노트가 성장하는 흐름을 만든다.
- 기술 학습, 프로젝트 경험, 개인 생각, 회고와 목표를 함께 관리한다.
- 파일명은 읽기 쉬운 한글 제목을 사용하고, 안정적인 식별자는 frontmatter에 둔다.
- 사실 노트는 공식 또는 1차 자료로 검증하고, 개인 경험과 해석은 사실 근거와 구분한다.
- 기존 고품질 노트를 선별해 승격하고, 저품질·중복·자동 생성 노트는 보관한다.

## 3. 비목표

- 강의 노트북, 코드, 데이터셋과 프로젝트 소스 전체를 볼트에 복사하지 않는다.
- 1,887개 원본 파일을 파일별로 요약하지 않는다.
- 개인 감정, 경험이나 목표를 원본 근거 없이 생성하지 않는다.
- 초기 전환에서 기존 노트를 영구 삭제하지 않는다.
- Dataview 같은 커뮤니티 플러그인을 필수 의존성으로 추가하지 않는다.
- `C:\MinHyeok\lecture`와 `C:\MinHyeok\skn26_projects`를 수정하지 않는다.

## 4. 전환 전략

같은 Obsidian 볼트 안에서 단계적으로 승격한다.

1. 새 Second Brain 폴더, 홈과 템플릿을 만든다.
2. 기존 `Knowledge`를 레거시 자료로 유지하면서 전체 목록과 링크 관계를 기록한다.
3. 검증된 핵심 노트만 새 구조로 재작성한다.
4. 5개 프로젝트와 12개 강의 영역의 진입점을 만든다.
5. 링크와 메타데이터를 검증한다.
6. 승격되지 않은 노트와 LLM 운영 자산을 `90 보관함/이전 LLM Wiki`로 이동한다.

이 방식은 전환 중 일부 중복을 허용하지만, 기존 자료를 비교·복구할 수 있고 링크 손상을 단계별로 발견할 수 있다.

## 5. 볼트 구조

루트 진입점은 `Second Brain 홈.md`다.

```text
Second Brain 홈.md
00 인박스/
10 데일리/
20 소스 노트/
  강의/
  프로젝트/
  공식 문서와 문헌/
30 영구 노트/
40 프로젝트/
50 영역/
60 구조 노트/
70 첨부 파일/
90 보관함/
  이전 LLM Wiki/
99 템플릿/
```

### 5.1 폴더 책임

- `00 인박스`: 분류 전 메모, 탐색용 링크, 아직 검증하지 않은 아이디어
- `10 데일리`: 일일 기록, 목표, 작업과 생각이 발생한 맥락
- `20 소스 노트`: 강의, 프로젝트, 공식 문서, 논문, 책과 웹 자료를 읽고 작성한 노트
- `30 영구 노트`: 내 말로 쓴 하나의 독립적인 주장, 통찰 또는 재사용 가능한 원칙
- `40 프로젝트`: 5개 프로젝트의 개요, 직접 기여, 판단, 실패, 회고와 관련 지식
- `50 영역`: 기술 학습, 커리어, 개발 원칙, 개인 목표처럼 종료 시점이 없는 책임 영역과 실용 레퍼런스
- `60 구조 노트`: 주제별 MOC와 학습·문제 해결 경로
- `70 첨부 파일`: 활성 노트가 직접 사용하는 이미지와 PDF
- `90 보관함`: 종료된 자료, 저품질 노트, 중복 노트와 이전 LLM Wiki
- `99 템플릿`: 데일리, 소스, 영구, 프로젝트와 회고 템플릿

## 6. 노트 생명주기

```text
인박스·데일리
    → 소스 노트
    → 영구 노트
    → 프로젝트·영역·구조 노트 연결
    → 보관 또는 계속 성장
```

- 탐색 중 발견한 링크와 아이디어는 `00 인박스`에 둔다.
- 출처를 실제로 읽은 뒤 `20 소스 노트`에 핵심 내용과 해석을 기록한다.
- 다른 맥락에서도 재사용할 수 있는 생각은 `30 영구 노트`로 분리한다.
- 영구 노트는 적어도 하나의 소스 노트와 하나의 내부 연결을 가져야 한다. 개인 회고에서 나온 주장이라면 개인 근거임을 명시한다.
- 프로젝트에만 해당하는 구현 사실은 `40 프로젝트`에 남기고, 일반화 가능한 교훈만 영구 노트로 분리한다.
- 더 이상 성장시키지 않거나 근거가 약한 노트는 삭제 대신 보관한다.

## 7. 파일명과 식별자

- 파일명은 한글 문장형 제목을 기본으로 한다.
- 기술 고유명은 `RAG`, `LangGraph`, `React`처럼 원래 표기를 유지한다.
- Windows 금지 문자 `\ / : * ? " < > |`는 사용하지 않는다.
- 영구 노트는 주제명보다 주장을 드러내는 제목을 우선한다.
- 고유 ID는 `YYYYMMDDHHmmss-xxxx` 형식을 사용한다. `xxxx`는 충돌 방지를 위한 영숫자 접미사다.
- 제목을 변경할 때 이전 제목은 `aliases`에 기록하고, 모든 내부 링크는 새 제목으로 갱신한다.

## 8. 공통 메타데이터

```yaml
---
id: 20260811143012-a1b2
type: permanent
status: growing
created: 2026-08-11
updated: 2026-08-11
tags:
  - rag
  - retrieval
aliases: []
sources:
  - "[[LangChain 공식 RAG 문서]]"
source_quality: primary
verified: true
---
```

### 8.1 허용 값

- `type`: `inbox`, `daily`, `source`, `permanent`, `project`, `area`, `structure`, `reflection`, `template`, `archive`
- `status`: `seed`, `growing`, `evergreen`, `archived`
- `source_quality`: `primary`, `secondary`, `discovery`, `personal`, `mixed`
- `verified`: `true` 또는 `false`

### 8.2 상태 전이

- `seed`: 아직 정리·검증하지 않은 인박스 또는 소스 초안
- `growing`: 출처와 내부 연결을 갖추어 재사용할 수 있는 노트
- `evergreen`: 내용을 다시 읽고 정확성, 표현, 연결과 한계를 검토한 노트
- `archived`: 활성 탐색과 검색에서 제외할 노트

검증되지 않은 사실은 `seed` 상태의 인박스 또는 소스 노트에 남긴다. 사실을 담은 영구 노트는 공식·1차 근거를 확인한 뒤 `growing`으로 승격한다.

## 9. 출처 정책

### 9.1 출처 등급

1. 주요 근거: 공식 문서, 논문, 표준, 책, 강의 자료, 실제 코드와 프로젝트 README
2. 보조 근거: Wikipedia, 신뢰할 수 있는 기술 블로그와 해설 문서
3. 탐색용: 나무위키, 커뮤니티 게시물과 AI 답변
4. 개인 근거: 직접 경험, 기술적 의사결정, 회고와 목표

### 9.2 승격 규칙

- 나무위키, 커뮤니티와 AI 답변은 주제를 발견하는 데만 사용한다.
- 중요한 사실은 공식 또는 1차 자료로 다시 확인한다.
- 2차 자료만 사용한 사실 노트는 `verified: false`를 유지한다.
- 개인 생각과 회고는 외부 출처 없이 작성할 수 있지만 `source_quality: personal`로 표시한다.
- 공식 자료와 프로젝트 경험이 함께 근거가 되면 `source_quality: mixed`를 사용한다.
- 출처가 충돌하면 최신 공식 문서와 실제 코드·최신 README를 기술 사실의 우선 근거로 사용하고, 충돌 내용을 소스 노트에 기록한다.

## 10. 노트 본문 모델

### 10.1 영구 노트

```text
# 주장형 제목

## 주장
내 말로 작성한 하나의 생각

## 근거
공식 자료, 강의 또는 프로젝트에서 확인한 근거

## 연결
기존 노트와의 관계

## 한계와 반례
항상 적용되지 않는 조건

## 다음 질문
더 탐구할 문제
```

기존 LLM Wiki의 사전식 정의, 동일한 사용 조건·금지 조건·체크리스트를 모든 노트에 반복하는 형식은 사용하지 않는다. 섹션은 내용에 필요한 경우에만 남긴다.

### 10.2 소스 노트

- 출처와 접근일
- 출처의 핵심 주장
- 필요한 최소 인용 또는 코드 위치
- 내 해석과 의문
- 분리할 영구 노트 후보

### 10.3 프로젝트 노트

- 프로젝트 개요와 기간
- 팀 산출물과 직접 기여 구분
- 기술적 의사결정: 상황, 선택, 이유, 실행, 결과, 회고
- 실패와 해결 과정
- 개인 성장과 다음 행동
- 관련 영구 노트
- 최신 README와 코드 경로

### 10.4 데일리·회고 노트

- 오늘 일어난 일과 현재 맥락
- 배운 점과 바뀐 생각
- 연결할 프로젝트·영역·영구 노트
- 다음 행동

## 13. 기존 노트 선별

### 13.1 우선 승격 후보

- `wiki-expanded` 상태의 설명과 근거가 충실한 개념 노트
- `source-expanded` 상태의 강의 노트
- 실용성이 높은 Reference Note
- 프로젝트 코드와 최신 README로 확인 가능한 경험 노트
- 개인 Dev Rules, 개발자 정체성, 의사결정·실패 로그와 회고 질문

Reference Note와 치트시트는 영구 노트로 억지 변환하지 않고 `50 영역`의 실용 레퍼런스로 배치할 수 있다.

### 13.2 기본 보관 후보

- `wiki-standardized` 상태의 얕은 자동 생성 노트
- 중복 정의와 상투적 문구만 있는 노트
- LLM 검색 정책, 검색 스코프, 품질 게이트와 전환 보고서
- 생성 목록, 인벤토리와 마이그레이션용 JSON
- 활성 Second Brain에서 더 이상 사용하지 않는 검색 스코프 갱신 도구

기본 보관 후보라도 강의·프로젝트 자료에서 직접 근거와 유용한 연결을 확인하면 재작성해 승격할 수 있다.

## 14. 링크 보존

1. 이동·이름 변경 전 모든 Markdown 파일과 wikilink를 목록화한다.
2. 기존 경로와 새 경로, 기존 제목과 새 제목의 매핑을 만든다.
3. 파일을 이동하거나 재작성한다.
4. 이전 제목을 `aliases`에 추가한다.
5. `[[노트]]`, `[[노트#제목]]`, `[[노트^블록]]` 링크를 매핑에 따라 갱신한다.
6. 활성 노트의 미해결 링크를 검사한다.

단순 파일 이동으로 제목이 유지되는 경우 불필요하게 링크를 다시 쓰지 않는다.

## 15. 오류와 불확실성 처리

- 원본을 읽을 수 없으면 내용을 추측하지 않는다.
- 출처가 없거나 충돌하는 항목은 `00 인박스/가져오기 검토 목록.md`에 원본 경로와 문제를 기록한다.
- 개인 기여가 팀 전체 구현과 구분되지 않으면 팀 산출물로 표시하고 직접 기여라고 단정하지 않는다.
- 외부 URL을 확인할 수 없으면 마지막 확인일과 미검증 상태를 남긴다.
- 동일한 주장의 중복 노트는 즉시 삭제하지 않고 대표 노트와 보관 후보를 기록한다.

## 16. Obsidian 설정 보존

현재 사용자 변경이 있는 다음 파일은 자동 전환에서 덮어쓰지 않는다.

## 17. 검증 기준

- 활성 노트에 `llm_wiki`, `wiki-*`, 이전 검색 정책 참조가 남지 않는다.

- 모든 ID가 허용 형식에 맞고 중복되지 않는다.
- `type`, `status`, `source_quality`가 허용 값만 사용한다.
- 깨진 내부 링크, `C:\lecture`, 이전 `C:\MinHyeok\skn26_*` 프로젝트 경로가 없다.
- 5개 프로젝트 허브와 12개 강의 구조 노트가 존재한다.
- `verified: true`인 사실 노트는 공식·1차 근거를 포함한다.
- 나무위키, 커뮤니티와 AI 답변만 근거로 한 영구 노트가 없다.
- 활성 노트에 빈 템플릿 문구와 자동 생성형 상투 문장이 없다.
- 원본 강의·프로젝트 폴더의 파일이 변경되지 않는다.
- 사용자의 기존 Obsidian 설정 변경이 보존된다.
- `Second Brain 홈.md`에서 주요 구조 노트, 프로젝트, 영역과 최근 작업 진입점으로 이동할 수 있다.

검증은 자동 검사와 수동 표본 검토를 함께 사용한다. 자동 검사는 frontmatter, ID, 링크, 이전 경로와 금지 상태를 검사한다. 수동 검토는 프로젝트별 최소 한 개, 강의 영역별 최소 한 개, 영구 노트와 회고 노트를 표본으로 확인한다.

## 18. 복구 전략

- 초기 전환에서는 영구 삭제하지 않고 `90 보관함`으로 이동한다.
- 각 단계는 독립된 Git 커밋으로 남긴다.
- 링크 검사에 실패하면 다음 단계로 진행하지 않고 해당 단계의 이동·재작성 매핑을 수정한다.
