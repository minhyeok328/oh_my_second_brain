# 프로젝트 회고 질문 세트

태그: #llm_wiki #questions #project #experience

## 목적

프로젝트 노트를 "기술 요약"에서 "내 경험이 들어간 second brain"으로 바꾸기 위해 사용자에게 확인해야 할 질문을 모은다. 이 질문은 답을 바로 요구하는 체크리스트가 아니라, 나중에 프로젝트별 회고를 채울 때 사용할 입력 큐다.

## 공통 질문

- 이 프로젝트에서 내가 직접 책임진 산출물은 무엇인가?
- 내가 처음부터 끝까지 설명할 수 있는 흐름은 어디까지인가?
- 가장 오래 막혔던 문제는 무엇이고, 결국 어떤 단서로 풀렸는가?
- 당시에는 맞다고 생각했지만 지금 보면 바꾸고 싶은 선택은 무엇인가?
- 발표나 문서에서 가장 자신 있게 설명할 수 있는 부분은 무엇인가?
- 다음 프로젝트에서 다시 쓰고 싶은 패턴은 무엇인가?
- 다음 프로젝트에서 피하고 싶은 방식은 무엇인가?

## 프로젝트 전체 회고

- 답변 완료:
  - 가장 큰 전환점: [[SKN26 2차 프로젝트 - 카드 이탈 예측]]
  - 이유: 기술 자체보다 문서 작업과 협업 규칙을 보며 팀 프로젝트에는 지켜야 할 것과 생각할 것이 많다는 것을 느꼈다
  - 구체적 계기: 커밋 컨벤션, Docker, CLI git, 브랜치 전략, 문서화
  - 다음 프로젝트에서 지키고 싶은 방식: 소통에는 한계가 있으므로 문서화를 가장 중요하게 두고, 그 다음 dev rules를 짜서 지킨다
  - 포트폴리오에서 보이고 싶은 모습: 기술도 중요하지만 협업을 위해 정말 많이 노력하는 사람
- 정리 노트:
  - [[프로젝트 기반 개발자 정체성]]
- 추가 확인:
  - dev rules에 반드시 넣고 싶은 항목: commit, branch, issue, docs
  - 포트폴리오에 넣을 협업 증거는 README, QA 리포트, GitHub 운영 기록, 문서 구조 중 무엇이 가장 강한가?
  - [[개인 Dev Rules]]를 실제 프로젝트 README나 CONTRIBUTING 문서로 옮긴다면 어느 정도까지 구체화할 것인가?

## 1차 차량 TCO

- 답변 완료:
  - 직접 맡은 부분: API 수집
  - 가장 어려웠던 점: 노베이스에 가까운 상태에서 코딩, AI, 에이전트와 친숙하지 않았던 첫 프로젝트였다는 점
  - 깨달음: 코딩은 많이 작성하고 가지고 놀아야 더 빠르게 흡수된다
  - 설명 포인트: 기술이 부족하더라도 최선을 다해 기본을 지켰다는 점
- 추가 확인:
  - 1차 프로젝트 자체를 다시 만든다면 어떤 구조를 먼저 바꾸고 싶은가?
- Streamlit 화면 흐름에서 가장 신경 쓴 사용자 행동은 무엇이었는가?
- `st.session_state`를 쓰면서 가장 헷갈렸던 상태값은 무엇인가?
- DB 조회를 `DBLoader.py`로 분리한 구조는 충분했는가, 아니면 더 나눴어야 했는가?
- 차량 모델 `LIKE` 검색에서 검색 결과가 모호할 때 어떤 UX가 필요하다고 느꼈는가?
- 외부 API/웹 수집 결과가 없을 때 계산을 중단할지, 기본값으로 계속할지 어떤 기준을 세웠는가?
- 월간 TCO 계산에서 가장 실수하기 쉬운 단위 변환은 무엇이었는가?

## 2차 카드 이탈 예측

- 답변 완료:
  - 직접 맡은 부분: 모델링에서 군집화와 차원축소 등 여러 접근을 시도하며 데이터 결측치를 역으로 추정하려 했다
  - Unknown Income 판단: 관계를 시각화했을 때 Unknown이 끼치는 영향이 커서 없애기 어려웠다
  - 성능 저하 원인 가설: 가장 먼저 불균형을 의심했다
  - Low/High binary 재구성: 문제 단순화보다 비즈니스 의미를 더 명확히 하는 선택이었다
  - 중요하게 본 지표: 이탈자 예측이라 당시에는 정확도를 더 집중적으로 보려 했던 것으로 기억한다
  - 협업 도구 경험: MLflow, Docker Compose, CLI git, 브랜치 전략이 모두 처음이라 어려웠지만 이후 프로젝트에서는 더 편해졌다
  - 다시 한다면: 결측치 예측을 다양한 방향에서 더 시도하고 결과를 명확히 마무리하고 싶다
- 추가 확인:
  - 정확도 외에 이탈자 class의 recall, F1을 어느 수준까지 봐야 실제 리텐션 의사결정에 쓸 수 있다고 느끼는가?

## 3차 PICKLE RAG 챗봇

- 답변 완료:
  - 직접 맡은 부분: RAG 구조, LLM 모델링, 모델 평가, Streamlit 기반 UI 구현
  - route 판단: fixed route는 굳이 필요했는지 의문이 남았다
  - 가장 흔들린 축: answer가 생각보다 어려웠다
  - LangGraph 판단: node를 나누면 관리가 더 쉬워질 수밖에 없다고 느꼈다
  - 평가 관점: LLM의 핵심인 RAG 평가는 얼마나 잘 참조하는지를 보는 것이어서 가장 중요했다
  - 답변 원칙: RAG의 핵심은 hallucination 방지이므로 후보 밖 답변 금지를 가장 신경 썼다
  - 다시 한다면: RAG 구조를 크게 바꾸기보다 더 세분화하거나 에이전트 파이프라인을 구축해 최신 트렌드를 실험해보고 싶다
- 추가 확인:
  - fixed route를 유지하려면 어떤 질문 유형에서 반드시 이득이 있어야 한다고 보는가?
  - 에이전트 파이프라인으로 확장한다면 route, search, evaluate, memory 중 무엇을 먼저 agent화하고 싶은가?

## 4차 LG Home

- 답변 완료:
  - 공식 프로젝트 역할: 프론트엔드 파트, 문서 작업, GitHub 조직 관리
  - SSR 편의성: 딱히 편했던 점은 크게 없었다
  - SSR 불편함: React 없이 SSR 구조를 맞추다 보니 작성하고 관리할 파일이 너무 많아졌다
  - 챗봇 난점: 후속 질문 처리가 어려웠다
  - 모델링/RAG 분리: 모델링 쪽은 직접 맡지 않아 잘 모른다
  - QA 리스크: CSRF, 로그인, JSON API, fetch 처리 관련 세부 리스크는 프론트 QA 평가 리포트 기준으로 본다
  - 개인 확장 동기: Django template SSR 방식이 아니라 React를 사용한 분리 구조로 만들고 싶었다
  - 실제 행동: 프로젝트 종료 후 혼자 `4th_project_change_react`로 재공학했다
  - React SPA 전환 후 판단: Django는 DB와 프론트엔드의 징검다리 역할만 하면 될 것 같다고 느꼈다
- 추가 확인:
  - GitHub 조직 관리에서 가장 어려웠던 규칙은 branch, PR, issue, review 중 무엇이었는가?
  - 후속 질문 처리가 어려웠던 이유는 state 유지, intent 재판단, slot 병합, 답변 문맥 중 무엇에 가까웠는가?
  - React SPA로 다시 만들 때 가장 먼저 분리한 화면 또는 API는 무엇이었는가?
