# SKN26 1차 프로젝트 - 차량 TCO

태그: #llm_wiki #project #skn26 #streamlit #mysql

## 한 줄 요약

차량 구매 판단을 초기 가격이 아니라 월 단위 총소유비용(TCO)으로 비교하기 위해, 차량 제원·연비·유가·소모품 교체 주기·정비 단가를 결합한 Streamlit 기반 계산 시스템이다.

## 문제 정의

차량 유지비는 연료비, 정비비, 세금처럼 항목이 흩어져 있어 사용자가 장기 비용을 직관적으로 비교하기 어렵다. 이 프로젝트는 유지비를 하나의 고정값이 아니라 주행 거리와 차량 등급에 따라 변하는 계산 모델로 분해했다.

## 사용한 지식

- [[Streamlit 기본 UI]]: 차량 검색, 등급/연도 필터, 계산 결과를 한 화면에서 입력·출력한다.
- [[Streamlit Session State]]: 검색 결과와 선택 차량 상태를 유지한다.
- [[MySQL Connector Python]]: `DBLoader.py`에서 MySQL에 접속해 차량 연비, 가격, 부품 데이터를 조회한다.
- [[SQL SELECT와 WHERE]]: 차량 모델명을 `LIKE` 조건으로 검색한다.
- [[Pandas DataFrame]]: 소모품 교체 주기와 예상 비용을 표로 정리한다.
- [[Requests]], [[동적 웹 스크래핑]]: 차량 가격, 연료, 유가 데이터를 외부 소스에서 수집한다.

## 프로젝트 예시

- `main.py`는 사용자 입력, DB 조회, 비용 계산, Streamlit 화면 출력을 한 흐름으로 묶는다.
- `DB_Side\DBLoader.py`는 환경변수 기반 DB 접속 설정을 사용하고, `sendquery`, `sendquerys_with_commit`, `db_search`로 조회를 분리한다.
- `API_Side\OilPrice.py`, `CarOil.py`, `CarPrice.py`는 외부 데이터 수집을 담당한다.

## 판단 기준

- 계산 로직과 입력 데이터는 분리해야 한다. 정비 단가가 바뀌어도 계산 구조가 바뀌면 안 된다.
- 모든 비용은 월 단위나 주행 거리 기준처럼 같은 비교 단위로 환산해야 한다.
- 외부 API 결과가 없거나 모델명이 모호할 때는 계산을 계속하지 말고 사용자가 입력 조건을 조정하게 해야 한다.

## 개인 회고

- 직접 맡은 부분: 외부 차량/가격/유가 데이터를 가져오는 API 수집 영역에 가장 많이 관여했다.
- 가장 어려웠던 점: 1차 프로젝트는 코딩, AI, 에이전트와 아직 친숙하지 않은 상태에서 진행한 첫 프로젝트라 전반적으로 어렵게 느껴졌다.
- 깨달음: 코딩은 이론만 보는 것보다 많이 작성하고 직접 가지고 놀면서 친해질수록 더 빠르게 흡수된다는 감각을 얻었다.
- 설명 포인트: 기술이 부족했더라도 팀이 최선을 다해 기본을 지키며 구현하려 했다는 점을 말할 수 있다.
- 추가 확인 필요: 1차 프로젝트 자체를 다시 만든다면 API 수집, DB 조회, Streamlit 상태 관리 중 어떤 구조를 먼저 바꾸고 싶은지 별도로 정리한다.

## 실패 조건

- DB 조회 문자열을 직접 조립하면 SQL injection과 특수문자 오류가 생길 수 있다.
- 월 주행거리가 0이거나 누락되면 교체 시기 계산이 왜곡된다.
- API 데이터와 DB 스키마의 컬럼 순서를 코드가 암묵적으로 의존하면 데이터 변경에 취약하다.
