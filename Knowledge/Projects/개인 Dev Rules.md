# 개인 Dev Rules

태그: #llm_wiki #project #experience #collaboration #dev_rules

## 한 줄 요약

내가 어떤 프로젝트를 하더라도 포기하지 않을 협업 규칙은 commit, branch, issue, docs다.

## 왜 필요한가

2차 프로젝트에서 문서 작업, 커밋 컨벤션, Docker, CLI git, 브랜치 전략을 경험하며 팀 프로젝트는 코드만 잘 쓰면 되는 일이 아니라는 것을 체감했다. 소통에는 한계가 있고, 기억은 쉽게 흐려지므로 규칙과 문서가 팀의 기준점이 되어야 한다.

이 규칙은 완벽한 개발 문화를 만들기 위한 것이 아니라, 팀원이 서로 덜 헷갈리고 같은 방향으로 움직이기 위한 최소 장치다.

## 포기 못할 4가지

### Commit

- 커밋은 작업의 결과가 아니라 변경 이유를 남기는 기록이다.
- 커밋 메시지는 Conventional Commit처럼 최소한의 형식을 맞춘다.
- 한 커밋에는 되도록 하나의 의도를 담는다.
- 나중에 문제가 생겼을 때 "왜 이 변경이 들어왔는가"를 추적할 수 있어야 한다.

### Branch

- 브랜치는 작업 흐름을 섞지 않기 위한 분리선이다.
- 기능, 수정, 문서 작업을 구분해 팀원이 현재 작업 범위를 이해할 수 있게 한다.
- 브랜치 이름은 작업 목적을 바로 알 수 있어야 한다.
- main 또는 배포 기준 브랜치에는 검토되지 않은 작업을 직접 섞지 않는다.

### Issue

- 이슈는 작업을 시작하기 전에 문제를 정의하는 자리다.
- 무엇을 하려는지, 왜 필요한지, 완료 기준이 무엇인지 적는다.
- 말로 정한 작업도 이슈로 남겨야 나중에 누락과 오해를 줄일 수 있다.
- 이슈가 없으면 작업의 시작점과 책임 범위가 흐려진다.

### Docs

- 문서는 팀의 공유 기억이다.
- 실행 방법, 환경 변수, 폴더 구조, API 규칙, QA 결과, 회고를 남긴다.
- 문서는 코드와 함께 업데이트되어야 하며, 오래된 문서는 없는 문서보다 위험할 수 있다.
- 문서화는 발표용 장식이 아니라 다음 사람이 프로젝트를 이어받게 하는 작업이다.

## 최소 체크리스트

- 작업을 시작하기 전에 issue가 있는가?
- 작업 목적에 맞는 branch에서 시작했는가?
- commit 메시지가 변경 이유를 설명하는가?
- PR이나 병합 전에 관련 docs가 같이 갱신됐는가?
- 팀원이 새로 들어와도 README와 docs만 보고 실행 흐름을 따라갈 수 있는가?

## 실패 조건

- commit이 너무 크면 원인 추적이 어려워진다.
- branch 규칙이 없으면 서로의 작업이 섞이고 되돌리기 어려워진다.
- issue 없이 작업하면 완료 기준이 사람마다 달라진다.
- docs가 오래되면 팀원이 잘못된 정보를 믿고 시간을 잃는다.

## 포트폴리오에서 말하는 방식

> 저는 프로젝트에서 commit, branch, issue, docs를 가장 중요한 협업 규칙으로 봅니다. 코드를 잘 쓰는 것도 중요하지만, 팀원이 변경 이유와 작업 흐름을 따라올 수 있게 만드는 것이 프로젝트 완성도를 높인다고 생각합니다.
