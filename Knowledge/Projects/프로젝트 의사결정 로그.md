### 외부 차량/가격/유가 데이터를 조합

## 2차 카드 이탈 예측

### 고객 행동 지표 중심으로 이탈을 해석

- 근거: README의 거래 횟수, 거래 금액, 사용률, 거래 변화율, 비활성 기간, 고객센터 접촉 분석
- 선택 이유: 나이, 학력, 소득보다 실제 사용 행동이 이탈 선행 신호에 가까웠다.
- 연결 노트: [[EDA]], [[Feature Engineering]]
- 개인 회고: 모델링 과정에서 군집화와 차원축소까지 포함해 여러 접근을 시도하며 결측치를 역으로 추정해보려 했다.

### Unknown Income을 삭제하지 않고 예측 보정 대상으로 분리

- 근거: `model_evaluation.md`의 known/unknown 분리와 XGBoost income classification
- 선택 이유: Unknown을 단순 삭제하면 데이터 손실이 생기고, 학습에 섞으면 label 의미가 흐려질 수 있었다.
- 연결 노트: [[Feature Engineering]], [[Train Test Split]], [[분류 평가 지표]]
- 개인 회고: 관계를 시각화했을 때 Unknown이 변수 해석에 끼치는 영향이 커서 없애기에는 부담이 컸다.

### Multi-class에서 Low/High binary 재구성 실험

- 근거: `model_evaluation.md`의 multi-class test accuracy 0.5989와 binary test accuracy 0.9027 비교
- 선택 이유: income 5개 class의 경계가 모호해 더 단순한 문제 정의가 성능과 해석에 유리했다.
- 연결 노트: [[분류 평가 지표]], [[XGBoost]]
- 개인 회고: 성능이 낮을 때 가장 먼저 의심한 것은 class 불균형이었다. Low/High 재구성은 단순한 편의보다 비즈니스 의미를 더 명확하게 만드는 선택으로 받아들였다.

### 모델과 실행 환경을 분리된 서비스로 구성

- 근거: `docker-compose.yaml`의 Streamlit, MLflow, pipeline API, DB 구성
- 선택 이유: 분석 화면, 실험 추적, ETL/API, DB를 각각 독립적으로 실행해야 했다.
- 연결 노트: [[Docker Compose]], [[MLflow]], [[FastAPI]]
- 개인 회고: MLflow와 Docker Compose뿐 아니라 CLI git, 브랜치 전략도 처음이라 어려웠다. 다만 처음의 어려움을 겪은 뒤에는 다음 프로젝트부터 협업 도구를 받아들이는 속도가 빨라졌다.

## 3차 PICKLE RAG 챗봇

### 질문을 fixed와 embedding route로 분리

- 근거: `src\router.py`, `src\pipeline.py`
- 선택 이유: 특정 식당/메뉴 질문과 분위기·상황 기반 추천 질문은 검색 전략이 달랐다.
- 연결 노트: [[RAG]], [[LangGraph]], [[Retriever]]
- 개인 회고: fixed route는 구현 후에도 굳이 필요했는지 의문이 남았다. 검색 전략을 분리하는 장점은 있었지만, route 자체가 복잡도를 만드는 선택이기도 했다.

### LangGraph로 route, slot, search, generate를 분리

- 근거: `GraphState`, `route_node`, `embedding_slot_node`, `fixed_slot_node`, `connector_search_node`, `generate_node`
- 선택 이유: RAG 실패가 어느 단계에서 났는지 분리해서 추적하기 위해서다.
- 연결 노트: [[LangGraph]], [[LangGraph State]], [[LangGraph Conditional Edge]]
- 개인 회고: node를 나누면 route, slot, search, generate를 단계별로 볼 수 있어 관리와 디버깅이 쉬워졌다고 느꼈다. 다음에는 구조 자체를 바꾸기보다 node를 더 세분화하거나 에이전트 파이프라인을 붙이는 방향을 실험해보고 싶다.

### Goldset 기반으로 RAG 품질을 평가

- 근거: `src_test3\build_llm_goldset.py`, `evaluate_llm.py`, fixed 20개 + embedding 30개 구조
- 선택 이유: 답변 문장만 보는 대신 route, payload, target, answer, retrieval을 분리해 평가했다.
- 연결 노트: [[RAG 평가]], [[RAG 평가 질문 세트]], [[RAG 검색 실패 사례]]
- 개인 회고: LLM 프로젝트의 핵심은 RAG 평가였고, 특히 검색 결과를 얼마나 잘 참조하는지가 중요했다. 평가 축 중에서는 answer가 생각보다 어렵게 느껴졌다.
